## 1. A1：PWA 新版本提示替代强制刷新

**现状**（`src/main.js`）：

```js
registerSW({ immediate: true, onNeedRefresh() { window.location.reload() }, onOfflineReady() {} })
```

**问题**：`onNeedRefresh` 在 SW 发现新版本时同步触发，用户无感知且正在进行的操作全部丢失。

**方案**：新增 `src/utils/swRefresh.mjs`（纯函数，零依赖，可 node 测试）：

```js
export function showRefreshPrompt({ push, reload, message = '有新版本可用' })
```

- 走 toast 的 `actionLabel` + `onAction`（既有能力，不新增 UI）
- `duration: 0` —— **不自动消失**，等用户自己决定（刷新是用户主动行为，不该被计时器替ta决定）
- `tone: 'info'`，按钮文案「刷新」

`main.js` 改为：`onNeedRefresh()` 里惰性取 `useToastStore()` 再调 `showRefreshPrompt`。

### 1.1 实施中发现的两个真问题（原方案没覆盖）

| 问题 | 后果 | 修法 |
|---|---|---|
| `vite.config.js` 是 `registerType: 'autoUpdate'` | registerSW 模板在 auto 模式下**根本不调用 `onNeedRefresh`**（它只挂 `activated` 监听器直接 reload，见插件源码 `dist/client/build/register.js` 38-47 行）。改 `onNeedRefresh` 等于改死代码，无提示刷新照旧 | 改成 `registerType: 'prompt'`（注释写明原因，`test-bundle` 第 9 节钉住） |
| `prompt` 模式下新 SW 停在 waiting | 此时 `window.location.reload()` 只会用**旧** SW 再跑一遍 → 提示又出现，用户以为点了没用（假刷新） | `reload` 传 `registerSW` 返回的 `updateServiceWorker`：发 skipWaiting，SW 拿到控制权后由 library 自己 reload |

`showRefreshPrompt` 的 `reload` 参数因此是「让新版本生效」的函数，**不是**字面上的 `location.reload`。

**不做的**：不做「倒计时自动刷新」、不做「刷新前保存草稿」—— 前者是把强制刷新换个形式，
后者要侵入每个表单。提示 + 用户点刷新已经消除数据丢失。

**验收**：`tools/console/test-sw-refresh.mjs`（17 条）—— 传 stub `push`/`reload`，断言
① 调用了 push ② `actionLabel` 非空 ③ `onAction` 触发 `reload` ④ `duration` 为 0（不自动消失）
⑤ 没有直接调用 reload（提示出现时不许自己刷）⑥ 连点只生效一次。
真机另由 `probe/v12-verify.mjs` 断言「SW 已注册 + 3 秒内没自动刷新 + 无新版本时不弹提示」。

## 2. I3：自然语言进命令面板

### 2.1 关键设计约束

`utils/intent.js` 的 `parseIntent` 返回的是**筛选条件**（categories/purposes/price/sort），
不是**命令**（切换主题/打开洞察）。而命令表的 `keywords` 是**拼音与英文**
（「切换主题」→ `zhuti`/`zt`/`theme`），用户打中文「深色」一个都命中不上。

所以需要一层**中文说法**。这与 `commands.js` 头部「手写拼音是刻意的」是同一条路线：
命令名短、意图明确，手写别名比猜输入习惯可靠。

### 2.2 新模块 `src/utils/commandPhrases.js`（纯函数、零依赖）

```js
export const PHRASE_MIN = 2
export const PHRASE_ALIASES = { '<命令 id>': ['中文说法', ...], ... }
export function matchPhrase(q, cmds)   // → { cmd, phrase, score } | null
```

**匹配算法**：
1. `norm(q)`：小写、去首尾空白
2. 对每条命令取 `PHRASE_ALIASES[cmd.id] || []`，找**被 q 包含的最长别名**
3. 分数 = 命中别名的字符数；同分按命令 id 稳定序（保证可重现）
4. `score < PHRASE_MIN` 返回 null

**别名表示例**（覆盖 page / view / action 三组的高频说法）：

```js
'view.theme':   ['深色', '暗色', '夜间', '黑暗', '浅色', '亮色', '换主题', '切换主题'],
'page.insights': ['洞察', '统计', '图表', '分析', '数据看板'],
'page.favorites': ['收藏夹', '我的收藏'],
'view.sort.clicks': ['按点击量', '点击量排序', '热门排序'],
...
```

### 2.3 交互（含「误命中一键退回」）

命中时在结果**最前面**插入一条 `type: 'phrase'` 的项：

- title = 命令标题（如「切换主题」）
- subtitle = `理解为：切换到深色 · ↓ 看其它结果`

**为什么不按路线图原写的「Esc 撤销」**：Esc 在 CommandPalette 里的既有语义是**关闭面板**，
接管它会与「按 Esc 关面板」的肌肉记忆冲突。改为 **↓ 即退回**：
phrase 项是第一项（默认选中），按一下下箭头就移到搜索结果，
语义无损且不与既有快捷键冲突。继续输入使 query 不再命中时，phrase 项自动消失。

**约束**：
- 只在**无前缀**时尝试（`>` / `@` / `/` 有明确语义，不让自然语言插手）
- `trimmed.length >= PHRASE_MIN` 才尝试
- inline（主页搜索框）与 palette（命令面板）**同一内核**，遵循 OmniBox「一个内核两个外壳」铁律
- phrase 项不改变 `groupOrder` 的既有阈值逻辑，只是强制置顶

### 2.4 接线点

`src/composables/useOmniBox.js`：
- import `matchPhrase` / `describePhrase` / `PHRASE_MIN`
- 新增 `phraseHint` computed：`prefix.value || page.value ? null : matchPhrase(trimmed.value, commands.value, phraseAliases.value)`
- `groups` computed 里，`phraseHint` 命中则 unshift 一个 `{ type: 'phrase', label: '理解', items: [phraseItem] }`
- `phraseItem.run` = 命令的 `run`
- 别名表 `ref` + 动态 `import('@/utils/phraseAliases')`（挂载即取，用户打字时兜底重试）

**实施修正：别名表拆成独立模块懒加载。** 原方案把 `PHRASE_ALIASES` 直接放在
`commandPhrases.js` 里导出，实测它 2.5 KiB 中文串把首屏从 589 顶到 **601.4 KiB（超 600 预算）**。
改为 `utils/phraseAliases.js` + `matchPhrase(q, cmds, aliases)` 第三参注入：

- 表没到时**优雅降级**：标题（×3）与特征名（×1）两级照常，「打开洞察面板」这类整句仍能命中；
  只有纯别名说法（「深色」）暂时不命中 —— 这一条 `test-command-phrases` 有专门断言。
- 契约用测试钉住：`matchPhrase(q, cmds, {})` 必须仍能命中整句标题（防止有人把表又 import 回去）。

**验收**：`tools/console/test-command-phrases.mjs`（**72 条**）
① 「切换到深色」→ 命中 `view.theme`
② 「打开洞察面板」→ 命中 `page.insights`
③ 「按点击量排序」→ 命中 `view.sort.clicks`
④ 单字（「暗」）不命中（低于 PHRASE_MIN）
⑤ 无意义输入（「asdfgh」）不命中
⑥ 多个命中时取**最长**别名（「切换到深色模式」优先整句而非「深色」）
⑦ 同分稳定序（两次调用结果一致）
⑧ 前缀输入不进匹配（由 useOmniBox 保证，纯函数层校验 matchPhrase 不看前缀）

## 3. E4：批量补全 + 轻量撤销栈

### 3.1 批量补三项（E4a）

`sites.js` 已有通用的 `batchUpdate(ids, patch)`（一次遍历 + 一次 rebuild），
所以新能力只是**包一层语义 + 快照原值供撤销**：

| 新 store 函数 | 实现 | 与单站行为的一致性 |
|---|---|---|
| `batchPin(ids)` | `batchUpdate(ids, { pinned: true, archived: false })` | 与 `togglePin` 一致：置顶同时退出归档 |
| `batchArchive(ids)` | `batchUpdate(ids, { archived: true, pinned: false })` | 与 `toggleArchive` 一致：归档同时取消置顶 |
| `invertSelection(visibleIds)` | 可见集中未选的加入、已选的移除 | 反选只对**当前可见**生效，不碰被筛掉的站 |

UI（`CardsContainer.vue` 的 `.batch-bar`）加三个按钮：置顶 / 归档 / 反选。
**不加框选**（与 masonry 的 CSS 多栏冲突，路线图已定）。

### 3.2 轻量撤销栈（E4b）

**为什么需要**：现在批量删/改错了只能去回收站翻，而改分类/加用途/置顶/归档**连回收站都进不去**
—— 改错了就改不回来。这是真实的数据安全缺口，不是锦上添花。

**新模块 `src/utils/undoCore.mjs`（纯函数、零依赖、可穷举测试）**：

```js
export const UNDO_MAX = 10      // 只留最近 10 步
export const UNDO_TTL = 5000    // 5 秒后可撤销窗口
export function pushUndo(steps, step)     // 入栈并裁剪到 UNDO_MAX（丢最旧）
export function dropExpired(steps, now)   // 清掉超过 TTL 的步
export function undoPatches(sites, ids, patch)  // 从当前站点算反向补丁
```

`undoPatches` 是核心：撤销要恢复**原值**而不是一律取反。
例如批量置顶时有些站本来已经是 pinned，撤销后它们应回到 pinned。
所以入栈前必须按当前值快照。

**新 store `src/stores/undo.js`**：
- `steps` ref + `push({ label, ops, kind })` / `take(id)` / `pop()` / `clear()`
- **session 持久化**（`encodeStored`/`decodeStored` 走 localStorage 的 `nav-undo-v1`），
  **不进站点表、不跨设备** —— 与备注/便签同一条纪律（公共数据会被发布冲掉）
- 不 import `sites.js`（避免循环依赖）

**接线落点：`src/composables/useUndoActions.js`**（实施时对原方案的修正）

原方案写的是「`sites.js` 加 `batchUpdateUndoable(ids, patch, label)`」。实施时改为独立组合式函数，理由：

1. 那三件事横跨**数据层**（sites：算反向补丁 + 执行）与**提示层**（toast：弹撤销入口）。
   放进 sites store 会让一个数据 store 开始依赖 toast —— 而项目既有纪律是
   「store 不改 UI、提示由组件发」（单站删除的撤销提示就写在 `App.vue` 里）。
2. 撤销入口有**两个调用方**：批量栏（`CardsContainer`）与 Ctrl+Z（`App.vue`），
   外加 OmniBox 的「撤销上一步」命令。放组件里会写三份，收敛成一个组合式函数才只有一份。

接口：

```js
useUndoActions() → {
  undoablePatch({ label, ids, patch, forward?, message })  // 改分类/置顶/归档/加用途
  undoableDelete({ ids, label?, message?, forward? })      // 删除（kind: 'restore'）
  undoStep(id)                                             // 撤回指定一步
  undoLast()                                               // Ctrl+Z：撤回最近一步
}
```

三个关键取舍：

- **`patch` 只用来指明要快照哪些字段**，具体值由 `undoPatches` 从站点当前值读 ——
  所以「每站补丁各不相同」的加用途也能走同一条路（传 `{ purposes: null }` + `forward`）。
- **`take(id)` 而不是弹栈顶**：提示会停留 5 秒，期间用户可能又做了别的批量操作，
  那时栈顶已经换人；按栈顶弹会撤错东西。撤销按钮撤的必须是**它自己那一次**。
- **提示存活时间 = 撤销窗口（`duration: UNDO_TTL`）**：提示还在就一定撤得回来，
  提示消失窗口也刚好过期。两者不一致就会出现「按钮还在但点了说撤不回来」。

**批量删除的撤销**：删除**不进补丁**（站点已不在列表里，没有「当前值」可快照），
改为 `kind: 'restore'` —— 撤销＝从回收站取回（复用既有 `restoreFromTrash`）。
未为它新造机制。`App.vue` 的单站删除也改走这条路径（`forward: deleteSite`），
这样 Ctrl+Z 撤的总是「刚刚那件破坏性的事」，不随操作规模变含义。

**UI 补丁（实施时新增）**：`ToastHost` 在批量栏可见时把提示抬到批量栏之上。
批量栏与提示都贴底且提示 z-index 更高（700 > 200），5 秒常驻的撤销提示正好盖住
「置顶 / 归档 / 改分类」——这是原方案没有预料到的交互冲突，截图复核时发现。
由 `v12-verify` 用**几何关系**断言（合成 click 会绕过命中测试，「点了有反应」证明不了没被盖住）。

**验收**：`tools/console/test-undo.mjs`（47 条）
① 入栈后 `steps.length === 1`
② 连续入 12 步 → 只留 10 步且丢的是**最旧**的
③ `dropExpired` 只清过期的，未过期的不动
④ `undoPatches` 对混合状态（3 个站 2 个已 pinned）算出**各自的原值**，不是一律取反
⑤ `undoPatches` 对不存在的 id 静默忽略
⑥ patch 里的字段与站点字段不一致时（站点无该字段）反向补丁为 undefined
⑦ `makeStep` 的 `kind` 默认 `patch`、非法值回落
⑧ 穷举：2^5 种 pinned × 2^5 种 archived 组合，全部置顶后撤销逐站回到原值

## 4. 不变量（本批次不可破）

1. **OmniBox 一个内核两个外壳**：I3 只改 `useOmniBox.js`，不往 CommandPalette / UnifiedSearchBox 单壳加逻辑。
2. **命令表仍是纯工厂**：`commandPhrases.js` 不 import store、不 import commands.js（别名按 id 对应，解耦）；
   别名**表**另成一模块，由调用方注入（懒加载，见 §2.4 实施说明）。
3. **session 纪律**：撤销栈走 localStorage（`nav-undo-v1`），**不进站点表**（公共数据会被发布冲掉），
   也不进 `services/session.js` 的同步白名单（没有跨设备意义）。
4. **首屏预算**：实测**未放宽**。原方案三项都不新增首屏 chunk，但实施时别名表（2.5 KiB 中文串）
   把入口顶到 601.4 KiB **超线 1.4 KiB** → 按本条预案把别名表拆懒加载，回落到 **599.0 KiB raw**。
   同批顺带把 `swRefresh.mjs` 也改成按需 import（「需要才用」而不是「点开才用」）。
   `test-bundle` 的 `LAZY_PARTS` 已点名这两块。
5. **不破坏既有断言**：`clicks` / `series` 双结构、`clickTier` 分档、roving tabindex 初值 0、
   焦点陷阱四处浮层 —— 全部保持原样。
6. **测试必须能「摘掉实现即失败」**：每个守卫用例都要临时抹掉实现验证会红。
