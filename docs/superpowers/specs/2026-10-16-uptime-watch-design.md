# 本站可用性监测 —— 设计文档

日期：2026-10-16
范围：本机工具（`shared/uptime.mjs` + `tools/console/lib/uptime.mjs` + `tools/cli/commands/uptime.mjs` + 计划任务）
起因：BotKeep 边缘入口当天故障约 6 分钟，站点全路径 503。当时只能靠人工连测确认，
「下次再挂，我手上没有时间线」。

---

## 0. 需求

给「我们自己部署的站点」加一道可用性防线：**自动探测 + 掉线区间落盘 + 出报告**，
并且下次故障时不用再靠人工盯着看。

## 1. 现状（改动前）

- **没有任何对本站可用性的监测**。有的只是：
  - `tools/console/lib/health.mjs` —— 探**收录的 300 个站点**（内容层面）
  - 平台自带的 uptime-kuma runtime —— **Free plan 只有 1 个 slot，已被 navigator-v2 占满**，装不了
- 故障时只能人工 `curl` 连测，事后没有任何记录；恢复时间、持续时长全靠回忆。

## 2. 方案

### 2.1 判定：把「平台挂了」和「我们挂了」分开

这是整件事里最要紧的一条。两类故障的处置**完全相反**：

| 判定 | 判据 | 该怎么办 |
|---|---|---|
| `edge-down` 平台边缘故障 | 响应体含 `Botkeep web access is temporarily unavailable` | 只能等它自愈；**重启容器治不了** |
| `app-down` 应用故障 | 有状态码但不是平台文案 | 看日志 / 考虑重启 |
| `network` 连不上 | 请求根本没到（DNS / 拒绝 / 超时） | 先查本机网络 |
| `ok` | 2xx / 3xx | —— |

判据是纯函数 `shared/uptime.mjs#classifyProbe`，可测（实测：平台故障时**连 `/api/health` 都返回平台文案**，
而我们的应用永远不会返回它）。

### 2.2 落盘与报告

- 每次探测一行 JSONL → `data/uptime.jsonl`（`/data/` 已 gitignore）；
- **有上限裁剪**：超 4 MiB 重写为最近 40000 行 —— 每 5 分钟一条、不封顶就是无界增长；
- 坏行（断电写一半）跳过并**如实计数**，不让整份历史读不出来；
- `foldOutages` 把事件序列折叠成掉线区间（进行中的段用 `now` 算时长；
  段内混合故障时取出现最多的那种 —— 它决定了要不要重启容器）；
- 可用率 = 在线时长 / 窗口时长；**没有样本时返回 `null` 而不是 100%**（不假装）。

### 2.3 让它一直跑：计划任务（照 `nav-console` 的成例）

**为什么不是常驻进程**：与 `nav-console` 同一套理由 —— 本机 Administrator 账户没有密码，
Windows 拒绝空密码账户做服务登录（1069）；而且常驻进程崩了没人拉起，计划任务由系统负责重来。

- 任务 `nav-uptime`：**AtLogOn + 每 5 分钟**触发一次 `nav uptime watch --samples 1`
  —— 每次只探一次就退出，幂等的观测动作，不需要看门狗；
- `IgnoreNew`：上一次还没探完（掉线时单次最长 12s 超时）就跳过这一轮，不堆叠实例；
- `-StartWhenAvailable`：错过触发（关机）后补跑。

**采样分辨率 = 触发间隔（默认 5 分钟）**，所以掉线起止的精度是 ±5 分钟。要更细就调小 `-Interval`。

### 2.4 通知：光记日志没人知道

状态变化时推一条通知（写入控制台通知中心 + 走已配置的 webhook）：

- 新增两个类型 `uptime.down` / `uptime.recovered`，**与 `health.*` 分开** ——
  后者说的是「我们收录的某个站点挂了」，混用同一个类型会让两类事在通知中心里分不清；
- `uptime.down` 带 30 分钟冷却：平台长时间故障时每 5 分钟一条会刷屏，冷却后仍能反映持续时长；
- **只在状态真的变化时推**。判据是「本次样本 vs **日志里上一条**」（不是「上一次调用」），
  所以「一次只探一个样本」的计划任务同样能识别变化 —— 这是 dedup 能成立的关键；
- 首次样本（没有上一条）不推，否则每次重启都报一次；
- 通知是**旁路**：`notify.push` 失败返回 null，绝不影响监测。

## 3. 命令

```bash
nav uptime check   --pretty          # 探一次，判定属于哪种故障（不落盘）
nav uptime watch   --interval 60 --pretty   # 持续盯：只在状态变化时出声，其余按心跳报平安
nav uptime watch   --samples 1       # 计划任务用的形态：探一次、落盘、退出
nav uptime report  --hours 24 --pretty      # 可用率 / 掉线区间 / 每段是谁的故障
```

## 4. 验收

| 项 | 方式 | 结果 |
|---|---|---|
| 判定 / 折叠 / 汇总 / 落盘与裁剪 | `tools/console/test-uptime.mjs` | **60 条** |
| 端到端：正常 → 掉线 → 同类再掉 → 恢复 | 真跑 CLI（日志走临时文件，不污染真实时间线） | 掉线推 1 条、**同类重复 0 条**、恢复推 1 条 |
| 计划任务 | `install-uptime.ps1` 注册后 `schtasks /Run` | 日志新增一条 200 样本 |
| 通知落点 | `nav ops notify --pretty` | 确认收到 `uptime.down` / `uptime.recovered` |
| 无回归 | `console:test:all` | 62 个脚本 |

**探针/测试的自我清理**：模拟用的假通知（`actor=uptime`）已按类型精确删除，
通知中心回到模拟前的 11 条；真实日志 5 条样本，0 条来自模拟地址。

## 5. 不做的事

- **不做常驻服务**：理由同上（空密码账户 + 单点进程更脆）。
- **不在平台上装 uptime-kuma**：Free plan 1 个 slot 已满，装它就得先删站点。
- **不推短信 / 邮件**：已有 webhook 通道，够用；要接第三个通道是另一件事。
- **不改线上后台**：监测跑在本机（本机才是「谁在看这个站」的现场）。
  新增的两个通知类型对线上是惰性的，线上不需要重新部署。
